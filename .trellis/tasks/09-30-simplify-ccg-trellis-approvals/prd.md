方案版本：`v1`。任务状态：`planning`。实施批准：**待用户审阅具体方案，尚未获得**。

## 目标与用户价值

对同一明确版本、范围和实施方案，只取得一次用户显式批准，并在 CCG 与 Trellis 间复用，减少任务记录、规划交接和生命周期切换造成的重复询问。继续保留计划批准、复杂任务文档、必要验证，以及独立后果性操作的审批。

## 需求与约束

| 编号 | 要求 |
|---|---|
| R1 | 直接请求创建任务、或明确授权创建的现有会话，不再为单纯记录任务额外问一次“是否创建”；未知实施方案不能继承这份授权。 |
| R2 | Trellis 存在时继续拥有唯一任务、需求、设计、实施计划、状态和完成权威。CCG 承接适用证据与质量门，避免另立一套相同计划的批准权威。 |
| R3 | 一次批准只覆盖用户已看见的具体任务、方案版本、实施范围、风险及动作。CCG 或 Trellis 已取得的同一批准可供另一层核对并引用，不重复索取。 |
| R4 | 缺少可核对来源、批准模糊、只批准建任务、拒绝、撤回、版本不符或实质变化时，保持/返回规划，并询问尚未覆盖的具体决定。 |
| R5 | 仅方案、范围或风险发生实质变化，或确有独立且必须批准的后果性操作时重请批准；说明变化及审批来源。格式、排版和交接入口的变化本身不新增用户审批。 |
| R6 | 复杂任务保留 PRD、design、implement；轻量任务保留现有 PRD-only 条件。保留快车道的既有/已批准条件，不能通过本任务实施尚未批准的快车道扩展。 |
| R7 | 保留实际变更所需的质量、安全、测试与文档门。Provider 调用/联网付费、安装、提交、推送、PR、合并、发布或破坏性操作的独立审批按其真实来源与授权范围核对，不冒用计划批准。 |
| R8 | 审批记录包含原文/引用来源、任务身份、方案版本与文件引用、覆盖范围和动作，以及明确的有效/未获批准状态；不伪造用户来源。 |
| R9 | 全部现有用户改动和未跟踪文件受保护。后续实施先建立隔离工作区并核对当前安装源；本次只新增本任务文档和调查证据，不改运行代码。 |

## 验收标准

- [ ] A1 → R1：已明确要求建任务时直接建立 `planning` 记录；不多问建任务批准，不变成 `in_progress`。
- [ ] A2 → R2/R3：Trellis 模式下以同一任务、同一实施方案承接 CCG→Trellis 和 Trellis→CCG；已有有效显式批准时两条方向均不重复提问。
- [ ] A3 → R3/R4/R8：用户对方案 `v1` 的可核对批准仅用于 `v1` 和已覆盖动作；仅“创建任务”、模糊“继续”、无来源的 approved 字段均不被当作未展示方案的实施批准。
- [ ] A4 → R4/R5：方案、范围、风险实质变化或独立未覆盖的后果性动作，仍停在相应门；格式调整或换用交接入口不新增审批。
- [ ] A5 → R6：复杂任务三份文档齐全；轻量与快车道条件不被扩张或取消，已有快车道任务保持原状态。
- [ ] A6 → R7：聚焦审批/交接测试及受影响仓库的必要离线门通过；不通过删除测试、缩窄现有门或关闭产品安全设置实现简化。
- [ ] A7 → R8：任务记录可指出批准来源、覆盖的具体版本/范围/动作；未批准/拒绝/撤回/失效状态明确，不假造批准。
- [ ] A8 → R9：最终改动名单与批准范围一致；原有 dirty 文件、索引、分支和 HEAD 得到核对及保护。

以上验收框是后续实施验收，本次创建方案不把它们标为实现完成。调查与文档检查的实测结果另见 `research/findings.md`。
